# TRAIL 프로토타입 UX 설문 (v2)

> **웹 버전: `/survey/ux`** — 배포·자극물·응답 내려받기는 [WEB.md](WEB.md). 문항을 고칠 때는 이 파일과 `lib/survey/ux.ts`를 같이 고친다.

## v1과 무엇이 달라졌나 — 측정 대상이 바뀌었다

v1은 **이 저장소의 앱 와이어프레임**을 쟀다. v2는 **Figma 프로토타입**(`https://reach-extra-11429501.figma.site/`)을 잰다. "가고 싶은 제품"이 기준이다.

프로토타입은 지금 코드와 **다른 제품**이다.

| | 배포된 앱 (v1이 측정) | 프로토타입 (v2가 측정) |
| --- | --- | --- |
| 탭 | Home · Trips · AI · Bags | **Home · Gifts · Wishlist · Bags** |
| 예산 | 3버킷 (Planned / Reserved / Flexible) | **한 줄** (`CAD $250` · `$39 spent` · `$211 left`) |
| 수령인 | 목록 | **1~4위 순위 + `TOP PRIORITY`** |
| 저장 | 없음 | **Wishlist (저장 → 나중에 픽업)** |
| 발견 | 지도 · 경로 | **위치 알림(`YOU'RE NEAR`) · `NEARBY NOW` · 자투리 시간 칩** |
| 배송비 | Pay 화면 | **`CAD $9 (pre-reserved)`, Bags 화면 안** |

**프로토타입에 없는 것**: 온보딩(여행·예산 등록), 지도/경로, 결제 화면, `Request` 버튼, 승인 게이트 화면, 3버킷 지갑.
→ 그 과업들(v1의 T1·T3, E1)은 **삭제하거나 화면 없이 답할 수 있는 개념 문항으로 바꿨다.**

### 문항 id를 재사용하지 않았다

**화면을 근거로 하는 문항은 전부 새 id다.** 같은 문장이라도 다른 화면 위에서는 다른 변수이고, 두 조사를 한 열에 합치면 CSV에서는 아무도 눈치채지 못한다.

유지한 id: `consent` · `s1`–`s5` · `d1`–`d3` · `b1`·`b2` · `f1`–`f5` · `umux` · `trust` · `nps` · `liked` · `fix` · `missing` · `beta`.
자극물과 무관하거나(스크리너·사전인식·실패 시나리오), 버전을 가로질러 읽으라고 만들어진 표준 척도(UMUX-Lite·NPS·신뢰)다. 그게 벤치마크의 존재 이유다.

폐기한 id: `c1`–`c3` · `t1_*`–`t6_*` · `e1`–`e5` · `p_*`(가격) · `ai`(AI 매트릭스).

> **Home이 두 장인 것은 의도다.** `p_home_top`은 **쉬고 있는 화면** — 시간 칩이 가려지지 않았고 어느 칩도 눌려 있지 않아서, T1의 `hour_first`가 "어디를 누를 것 같나"가 아니라 **실제 첫 클릭**이 된다. `p_home`은 같은 화면에 위치 알림 배너가 덮인 상태이고, 알림을 판단할 수 있는 유일한 프레임이다. **배너가 시간 칩을 가리므로 둘은 서로 대체할 수 없다.**
> `p_time_1h.png`는 쓰지 않는다 — `p_home.png`와 사실상 같은 프레임이다.
> 순서상 5초 테스트(`p_home`)는 화면이 사라진 뒤이므로, T1에서 배너 없는 Home이 나와도 나란히 놓고 비교되지 않는다. §위치 알림의 지시문이 배너가 "걸어가는 동안 떠올랐다"고 밝힌다.

## §2. 첫인상 (`p_home`, 5초)

`fi1` 무엇을 하는 서비스로 보였나 / `fi2` 가장 먼저 눈에 들어온 것 / `fi3` 나에게 필요할 것 같다 (1–7)

> **분석**: `fi1`을 "쇼핑 계획 / 짐 배송 / 위치 추천 / 여행 일정 / 모르겠다"로 코딩한다.
> v1의 실패선은 "짐 배송 언급 30% 미만"이었다. **v2에서는 이 기준을 그대로 쓸 수 없다** — 프로토타입 Home 첫 화면은 배송을 아예 보여주지 않고 위치 알림이 화면 최상단을 차지한다. v2에서 읽어야 할 것은 **"위치 추천" 언급률**이고, 배송 언급률이 낮은 것은 화면의 실패가 아니라 화면의 설계다. 다만 **배송이 유일한 수익 기능**이므로 이 수치는 그대로 사업 리스크다.

## §3. 과업 (T1–T7)

과업 공통 3문항(`_done` / `_seq` / `_note`)은 v1과 같다. T4와 T7만 `_done`을 빼고 `_seq`·`_note`만 붙인다 — 읽기 과업이라 "끝냈습니까"가 성립하지 않는다.

### T1 — 한 시간이 비었다 (`p_home_top` + `p_ai`) — **신설 · 실제 과업**

> 지시문: "토론토 2일차, 저녁 전에 한 시간이 비었고 선물 쇼핑을 좀 해두고 싶다."

- `hour_first` 🔑 **first click** — 어디부터 가겠나 *(시간 버튼 줄 / 입력창 / 준비된 질문 / 매장 카드 / 통계 박스 / 탭바)*
- `hour_chips` `1 hour`를 누르면 앱이 무엇을 한다고 기대하나 *(한 시간 안에 갈 수 있는 것만 추림 / 순서와 시간이 붙은 동선 / 채팅으로 답함 / 기억만 하고 화면은 그대로 / 모르겠다)*
- `hour_effect` 한 시간이라고 말한 뒤 **무엇이 달라져야 하나** *(복수 — 거리 / 대상 인원 / 스톱 수 / 지출 / 별로 없다)*
- `hour_knows` 앱이 도시·날짜·4명·잔액을 **이미 알고 있는 것**이 어떻게 읽혔나 *(유용 / 당연 / 확인부터 하고 싶다 / 과하다)*

> **`p_home_top`이 이 과업을 기대 질문에서 과업으로 바꿨다.** 배너에 가리지 않은 시간 칩이 보이고, **네 칩 중 어느 것도 눌려 있지 않다.** 그래서 `hour_first`는 실제 첫 클릭이고, 그 다음에야 `hour_chips`가 "그걸 누르면 무슨 일이 일어난다고 보나"를 물을 수 있다.
> **분석**:
> - `hour_first` == `chips` 비율이 곧 **자투리 시간 입력의 발견율**이다. **40% 미만이면 칩은 있어도 안 쓰인다** — 인사말 바로 아래, 가장 좋은 자리에 있는데도 그렇다면 자리가 아니라 형태의 문제다.
> - `hour_chips`의 분포는 칩을 눌렀을 때 만들어야 할 화면의 요구 사양이다. `remember`(기억만 한다)가 다수면 칩은 **필터가 아니라 설정**으로 읽히는 것이고, 그렇게 만들면 아무 일도 안 일어나는 버튼이 된다.
> - `hour_effect`에서 "별로 없다"가 30%를 넘으면 자투리 시간 입력은 **장식**이다.
> - `hour_knows`의 "과하다"는 §위치 알림의 `near_ok`와 함께 읽는다.

### T2 — 선물 받을 사람들 (`p_gifts`) — **신설**

- `pe_rank` 🔑 이름 옆 숫자 1~4는 무슨 뜻인가 → **정답 `order`(먼저 처리할 순서)**
- `pe_reorder` 순위를 어떻게 바꾸겠나 *(드래그 / AI에게 / 상세 진입 / 금액 조정 / 못 바꿀 것 같다)*
- `pe_means` 1위라면 **무엇이 달라져야 하나** *(복수 — 동선 / 배분액 / 시간 부족 시 우선 / 추천 품질 / 정렬일 뿐)*
- `pe_icons` 이름 옆 그림(🌸💼👯✨)을 어떻게 읽었나 *(구분에 도움 / 장식 / 뜻을 모르겠다 / 가벼워 보인다)*
- `pe_myself` `Myself`가 나머지 셋과 같은 목록에 있는 것

> **`pe_rank` 주의**: 1위 Mom이 배분액도 최대($80)라 오답 `money`가 정답과 공변한다. **그것 자체가 화면의 결함**이므로 `money` 선택률을 따로 집계한다.
> **`pe_icons`를 넣은 이유**: 프로토타입은 이모지를 수령인 **식별자**로 쓰고, 같은 이모지를 드롭오프 화면의 **가방 태그**까지 끌고 간다(`Mom 🌸 1 bag`). 매장 직원이라는 낯선 사람이 읽는 유일한 UI다. 취향이 아니라 기능이므로 기능으로 묻는다. 우리 디자인 규칙(구조적 아이콘에 이모지 금지)과 충돌하는 지점이고, `tell`이 압도적이면 규칙을 재검토할 근거가 된다.

### T3 — 나중에 살 것 (`p_wishlist`) — **신설**

- `sv_save` 🔑 여기 저장하면 무슨 일이 일어나나 → **정답 `note`(나에게 남기는 메모)**
- `sv_tilde` 🔑 `~CAD $42`의 물결표 → **정답 `about`(대략 그 정도, 실제가 다를 수 있다)**
- `sv_when` 이런 목록을 언제 쓰겠나
- `sv_instock` 이 물건들이 실제로 그 매장에 있을 것이다 (1–7) → 4점 이하면 `sv_why` 분기

> **`sv_save`가 v1의 `e1`(`Request`=재고 문의)을 대체한다.** 버튼은 사라졌지만 규칙은 그대로다 — **Trail은 매장과 거래하지 않는다.** `hold`(매장이 빼둔다)나 `order`가 30%를 넘으면 프로토타입은 하지 않는 일을 약속하고 있다.
> **`sv_tilde`**는 헌법 4번의 "실제가 예산 초과" 분기의 전조다. 물결표가 안 읽히면 매장에서의 가격 차이는 전부 앱의 거짓말로 귀속된다.

### T4 — 쓸 수 있는 돈 (`p_gifts` + `p_bags`) 🔑 — **전면 재작성**

> 지시문: "같은 여행, 같은 오후의 두 화면이다."

프로토타입에는 `Flexible`도 `Reserved for delivery`도 없다. 화면에 있는 숫자는 이것뿐이다:

```
Gifts  : CAD $250   ·   CAD $39 spent   ·   CAD $211 left
         Mom 80  ·  Friends 70  ·  Coworkers 45 (✓ $39)  ·  Myself 35
Bags   : Cost  CAD $9 (pre-reserved)
```

| 문항 | 정답 | 왜 자명하지 않은가 |
| --- | --- | --- |
| `mo_left` 아직 쓸 수 있는 금액 | **CAD $211** | 화면에 인쇄돼 있다. 틀리면 계산이 아니라 **읽기**의 실패다. 기준선 문항 |
| `mo_free` $250 중 **아무에게도 배정되지 않은 금액** | **CAD $20** | 어디에도 인쇄돼 있지 않다. 80+70+45+35 = **230**, 즉 20이 떠 있는데 진행바는 그 사실을 전혀 드러내지 않는다 |
| `mo_fee` `CAD $9 (pre-reserved)`로 배송하면 $211은 | **`same` — $211 그대로** | $211 = 250 − 39 **정확히**. 즉 $9는 쇼핑 금액에서 빠진 적이 없다. 그런데 "pre-reserved"라는 단어는 정확히 반대쪽으로 끈다 |

- `mo_sure` 확신도 (1–7)
- `mo_prereserved` "pre-reserved"를 자기 말로 (서술)
- `mo_over` $250을 넘기면 무슨 일이 일어난다고 보나 *(막는다 / 경고만 / 어디서 뺄지 묻는다 / 아무 일도 / 모르겠다)*
- `mo_drop` Gifts 화면에서 없어도 될 것 *(복수)*

> **분석**:
> - `mo_left` 정답률 **90% 미만이면 예산 줄이 안 읽히는 것**이다. 인쇄된 숫자다.
> - `mo_free` 정답률 **50% 미만이면 배분 모델이 화면에 존재하지 않는 것**이다. 수령인별 금액은 장식이 된다.
> - `mo_fee`에서 `already`/`drops`를 고른 비율이 곧 **"pre-reserved"라는 단어의 비용**이다. 40%를 넘으면 그 단어를 버린다.
> - `mo_over`는 정답이 없다 — 프로토타입은 아무것도 말하지 않는다. **분포가 곧 승인 게이트 화면의 요구 사양이다.**
> - v1의 `t4_remaining`(정답 $34, flexible 제외)과 **비교 불가**. 3버킷이 없는 제품이다.

### T5 — 손에서 내려놓기 (`p_bags`) — **재작성**

- `co_goes` 🔑 이 화면의 4개 중 오늘 저녁 호텔로 가는 것은 → **정답 `bought`(이미 산 초콜릿 1개뿐)**
- `co_partner` `Blue Banana Market`은 무엇인가 → **정답 `dropoff`**
- `co_how` 🔑 가방은 어떻게 거기까지 가나 → **정답 `walk`(내가 걸어서 가져간다)**
- `co_extra` **플랜 외 가방** — 앱이 모르는 매장에서 산 코트도 같이 보낼 수 있나
- `co_charge` $9는 언제 빠져나가나
- `co_worry` 이 단계에서 불안한 것 *(복수, `mix`(엉뚱한 사람에게 갈까 봐) 추가)*

> **`co_goes`가 이 조사에서 두 번째로 중요한 문항이다.** 화면은 **4개를 나열하고 1개를 보낸다**(`Items 1 purchased bags`). `all`을 고른 비율이 곧 "저장 항목이 배송된다고 오해하는" 비율이고, 그건 실제 서비스에서 호텔에 3개가 없는 사고로 나타난다.
> **`co_how`**: 프로토타입은 이송 모델을 **한 번도 말하지 않는다.** 사용자가 직접 들고 걸어간다는 사실이 안 읽히면(`pickup` 다수) 사업 모델이 통째로 오해된다.
> **`co_extra`**: 손그림 주석의 "플랜 외 가방". 화면에 답이 없다 — 분포가 요구 사양이다.
> **`co_charge`**: 프로토타입에 결제 화면이 없어 정답이 없다. 예약(hold)과 청구(charge)를 분리한 우리 모델이 화면 없이 전달되는지 본다. 분포가 넓으면 **결제 화면이 필요하다는 증거**다.

### T6 — 매장 카운터 (`p_dropoff`) — **재작성**

- `ct_clear` 이 화면만 보고 매장에서 뭘 해야 할지 알겠나 (1–7)
- `ct_count` 가방 개수는 누가 확인하나 → **정답 `both`** (2단계 직원이 태그 부착, 3단계 `Confirm the number of bags on screen`)
- `ct_tag` 직원이 **이름과 그림이 붙은 태그**를 가방마다 단다 — 어떤가 *(괜찮다 / 이니셜만 / 이름 없이 / 모르겠다)*
- `ct_time` 🔑 4단계는 `by 7:00 PM`, 앞 화면은 `Estimated 6:30–7:00 PM` — 어떻게 읽었나 *(약속 / 추정 / 두 화면이 다르다는 걸 알아챘다 / 시각을 못 봤다)*
- `ct_odd` 앞 화면과 달랐던 것 *(서술, 선택)*

> **`ct_time`이 헌법의 "확정어 금지"를 직접 재는 문항이다.** `promise`가 다수면 프로토타입 카피는 이미 지킬 수 없는 약속을 하고 있다. `clash`(모순 인지) 비율은 별도 집계한다.
> **`ct_tag`**는 선물 받는 사람 이름이 **낯선 사람에게 노출되는** 유일한 지점이다. `nonames`가 20%를 넘으면 태그 설계를 다시 한다.
> ⚠️ **프로토타입 결함**: Bags 화면은 `1 purchased bags`인데 이 화면은 **가방 3개**(Mom·Friends·Coworkers)를 보여준다. `co_goes` 응답을 오염시키지는 않는다(순서상 뒤에 나온다). `ct_odd`가 이 모순을 데이터로 잡는다.

### T7 — 걸어 나온 뒤 (`p_tracking`) — **재작성**

- `ow_where` 가방은 지금 어디 있나 → **정답 `transit`**
- `ow_calm` 얼마나 안심되나 (1–7)
- `ow_more` 더 있어야 할 정보 *(복수, `contents`(가방별 내용물) 추가)*
- `ow_late` **7시 20분인데 아직 `On the way`** — 무엇부터 하겠나 *(기다린다 / 앱에서 신고 / 호텔에 전화 / Trail 전화번호를 찾는다 / 모르겠다)*

> **`ow_late`가 아직 화면조차 없는 "지연·이상 신고"의 요구 사양이다.** `app`이 다수면 그 화면을 만들어야 하고, `trail`(전화번호를 찾는다)이 다수면 **연락 수단이 없다는 사실 자체가 실패 분기**다.
> ⚠️ 이 화면의 헤더가 아직 `Drop your bags`다(프로토타입 결함). `ow_calm`을 낮게 만들 수 있으므로 `_note`를 함께 읽는다.

## §4. 개념 이해도 (전 과업 종료 후) 🔑

화면이 없는 것을 화면 없이 묻는다. **응답자에게 정답 여부를 알리지 않는다.**

- `c_pay` 🔑 물건값은 누가 내나 → **정답 `me`(내가 매장에서)**
- `c_over` 매장 실가가 계획보다 CAD $40 비싸다. 앱은 **어떻게 해야 하나** → 제품의 답은 `propose`
- `c_where` 저장했지만 안 산 물건은 어느 탭에서 찾겠나 *(Gifts / Wishlist / Bags / 아무 데나 — 다 같아 보인다 / 모르겠다)*
- `c_demo` 데모·샘플·시뮬레이션 표기를 본 적 있나 → 있으면 `c_demo_where`
- `c_auto` 승인 없이 스스로 해도 되는 것 *(복수 — 추천 / 순위 변경 / 위치 알림 / 예산 이동 / 항목 삭제 / 배송 신청 / 배송비 결제 / 없음)*

> **`c_pay`를 남긴 이유**: 프로토타입에는 **결제 화면도, 계산대도 없다.** `$39 spent`와 `✓ $39`와 `Arrange delivery → CAD $9`만 있어서, 앱이 대신 결제한다고 읽을 여지가 v1보다 **더 크다.** id는 바꿨다(근거가 되는 화면이 통째로 달라졌으므로).
> **`c_over`를 남긴 이유**: 승인 게이트 화면이 없다. 그래서 "앱이 어떻게 한다고 보나"가 아니라 **"어떻게 해야 하나"**로 바꿔 물었다. 화면이 없을 때는 이해도가 아니라 **기대**를 재는 것이 정직하다. `propose` 지지율이 곧 승인 게이트의 지지율이다.
> **`e1`(Request)은 삭제했다.** 버튼이 없다. 규칙은 `sv_save`가 이어받았다.
> **`c_demo`**: 프로토타입에서 표기는 `Simulate walking notification`의 `DEMO` 칩 하나뿐이고, 재고·도착시각·QR·요금 어디에도 없다. **인지율이 낮게 나오는 것이 정상이며, 그게 헌법 3번 위반의 증거다.**
> **`c_where`**: Gifts·Wishlist·Bags가 모두 "살 것"을 담는다. 저장 항목은 Wishlist와 Bags **양쪽에** 나온다. 정답이 하나가 아니므로 분포와 `any` 비율을 읽는다. `any`가 25%를 넘으면 4탭 IA가 무너진 것이다.

## §7. 지불의사 (van Westendorp) — **id 전면 교체**

> 제시문: "그날 산 것 전부(쇼핑백 1~3개)를 지나가는 길에 파트너 매장 카운터에 맡기면, **그날 저녁 6시 30분~7시 사이에** 호텔 프런트로 간다. 남은 하루 동안 아무것도 들지 않는다."
> **주의: `CAD $9`를 이 섹션 앞에 다시 노출하지 않는다.** 앵커링이 걸리면 PSM 곡선이 무의미해진다.

`pr_expensive` / `pr_pricey` / `pr_cheap` / `pr_toocheap` — 4점 (CAD, 정수)
`pr_intent` — **CAD $9면 쓰겠는가** (1–7)
`pr_window` — 가방을 맡길 때 **무엇을 듣고 싶은가** *(추정 구간 6:30–7:00 / 늦어도 7시 / 늦어도 7시라면 돈을 더 내겠다 / 모르겠다)*
`pr_who` — 이 비용은 누가 내야 하나

> **왜 도착 시각 약속을 되살렸나**: 사용자가 배송비 $9와 도착 시각 약속을 **제품 방향으로 확정했고**, 프로토타입이 그것을 화면에 쓰고 있다. v1은 "카운터에서 구간을 알려준다"까지만 팔았다.
> **왜 id를 전부 바꿨나**: 파는 물건이 달라졌다. 설명문이 다른 두 조사의 PSM 곡선을 한 장에 겹치면, 그건 두 모집단을 지나는 한 개의 선이다.
> **`pr_window`가 가격과 카피를 잇는다.** `paymore`가 유의미하면 확정 도착이 **유료 옵션**이 되고, 그러면 "확정어 금지"는 카피 규칙이 아니라 **요금제 경계**가 된다.

### v1과 비교할 수 없는 것

`umux` · `trust` · `nps` · `f1`–`f5` · 스크리너 · `b1`은 v1 응답과 합쳐 읽어도 된다.
**나머지는 전부 다른 제품에 대한 응답이다.** 특히:

- **지갑 정답률** — v1은 `planned − spent`(잠긴 flexible 제외)를 쟀고 v2는 인쇄된 한 줄을 읽는다. 난이도 자체가 다르다.
- **가격** — 도착 시각 약속이 붙었다. 곡선을 겹치지 않는다.
- **첫인상** — v1 Home은 `Plan with TRAIL`, v2 Home은 위치 알림이 최상단이다.
- **AI 수용** — v1은 온보딩 대화, v2는 인사 한 줄이다.
