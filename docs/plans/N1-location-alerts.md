# N1 · 위치 기반 알림 — 실행 계획

`docs/BACKLOG_NEXT.md` N1을 착지시킨다. 셋 중 **가장 위험하고 가장 나중**이며, 이 문서의 결론은
**기능을 줄이는 것이 아니라 웹이 실제로 할 수 있는 것에 맞추는 것**이다.

이 문서는 계획이다. 코드는 한 줄도 고치지 않았다.

---

## 0. 이 기능이 실제로 만들어내는 것

사용자의 말은 이랬다.

> "gps켜놓도록 만들면 (…) 위치기반으로 알림을 주는거지! 여기 근처에 뭐있어! 이런식으로"

그 문장을 데이터로 옮기면 이렇게 된다.

> **"이 사람은 지금 이 좌표에 있고, Mom에게 줄 다기 세트를 아직 안 샀다."**

`VENTURE_BRIEF` §7.4는 TRAIL이 이미 **호텔명 + 숙박 날짜 + 시간대별 이동 경로 + 구매 내역 +
실명**을 안다고 적고, 그것을 "스토킹 등급 데이터셋"이라 부른다. N1은 거기에 **초 단위 현재 위치**를
더한다. G6이 공유에서 막은 것(`hotel_name` + `eta_start/eta_end` = 부재 시간표)은 **추론된**
부재였다. N1이 만드는 것은 **측정된** 현재다. 한 단계 더 나쁘다.

그래서 이 문서의 기본값은 G6과 같다: **필요한 것만 켠다. 좌표는 기본이 "저장하지 않음"이 아니라
"저장 불가능"이어야 한다** — 저장 경로 자체를 만들지 않는다.

동시에 이 기능은 **하지 않기로 하는 게 답이 아니다.** G3가 이미 `useNearby`로 좌표를 기기에서만
쓰는 길을 열어 놨고, N1은 그 길의 연장선에서 90% 성립한다. 성립하지 않는 10%는 "앱이 꺼져 있을
때도 알려준다"이고, **그건 웹에서 불가능하다.** §1이 그 판정이다.

## 1. 웹 플랫폼 판정 — 되는 것과 안 되는 것

### 1.1 결론 한 줄

> **백그라운드 지오펜스는 웹에서 불가능하다.** 브라우저만으로도, 서버를 붙여도 불가능하다.
> N1이 배포할 수 있는 것은 **앱이 실행 중일 때의 근접 알림**뿐이다.

### 1.2 근거 — API 하나씩

| API | 판정 | 사실 |
| --- | --- | --- |
| `navigator.geolocation.watchPosition` | **되지만 포그라운드 한정** | 문서가 살아 있는 동안만 콜백이 온다. iOS는 앱/탭이 백그라운드로 가면 JS를 정지시키고, Android Chrome은 백그라운드 탭의 타이머를 throttle한 뒤 수 분 내 freeze한다. 화면이 꺼지면 끝이다 |
| `ServiceWorkerGlobalScope`의 위치 | **없다** | **서비스워커에는 `navigator.geolocation`이 노출되지 않는다.** 어느 브라우저에서도. 이 한 줄이 "SW가 백그라운드에서 위치를 보고 알림을 띄운다" 설계 전체를 무효로 만든다 |
| W3C **Geofencing API** (`GeofencingManager`) | **존재하지 않는다** | 2015~2016 스펙 초안 이후 **어떤 브라우저도 출시하지 않았고** Chromium은 폐기했다. 웹에는 지오펜스 프리미티브가 없다 |
| **Periodic Background Sync** | 도움 안 됨 | Chromium 전용 + 설치된 PWA + 사이트 engagement 필요 + 주기는 브라우저 재량(실측 수 시간). **그리고 SW에 위치가 없으므로**(위 항목) 깨워봐야 판정할 것이 없다 |
| **Background Sync**(1회성) | 도움 안 됨 | 네트워크 복구 시 재전송용. 위치와 무관하고 Safari 미지원 |
| **Notification Triggers** (`TimestampTrigger`) | **없다** | Chrome 오리진 트라이얼로 끝났고 정식 출시된 적이 없다. 있었어도 **시간** 트리거지 위치 트리거가 아니다 |
| `Notification` 생성자 | 안드로이드에서 throw | Android Chrome은 `new Notification()`을 금지한다. **`registration.showNotification()`으로만** 띄울 수 있고, SW에 `notificationclick` 핸들러가 있어야 탭이 열린다 |
| `PushManager.subscribe` | **되지만 서버가 필요** | `userVisibleOnly: true` 강제(사일런트 푸시 불가). 그리고 푸시는 **우리 서버가 보낸다** — 언제 보낼지 알려면 **서버가 사용자의 현재 위치를 알아야 한다.** 이것이 §2의 Q1·Q4가 같은 질문인 이유다 |
| `navigator.permissions.query({name:'geolocation'})` | **믿지 마라** | Safari의 Permissions API 지원은 부분적이고 `geolocation` 조회는 신뢰할 수 없다. throw/미지원을 **"모름"**으로 다루고, 이 값만 보고 UI를 그리지 않는다. 진짜 권한 상태는 `getCurrentPosition`의 콜백뿐이다 |
| iOS/iPadOS **Web Push** | **홈 화면 웹앱 전용** | 16.4+에서 지원되지만 **"홈 화면에 추가"된 standalone 웹앱에서만**이다. 일반 Safari 탭에서는 `window.Notification`이 **undefined**다 → 반드시 feature detect. 권한 요청은 사용자 제스처에서만 |
| iOS 홈 화면 웹앱의 백그라운드 | **정지된다** | 푸시 권한이 있어도 **우리가 로컬 알림을 만들 수 없다.** 앱이 백그라운드면 JS가 안 돈다. 백그라운드 알림은 오직 **서버 푸시**로만 오고, 서버 푸시는 서버가 위치를 알아야 한다 |

### 1.3 이 판정이 낳는 두 갈래

```
백그라운드 알림을 원한다  →  서버가 위치를 알아야 한다  →  §2 Q1이 "저장한다"로 뒤집힌다
좌표를 기기 밖으로 안 낸다  →  알림은 앱이 실행 중일 때만  →  기능 범위가 줄어든다
```

**후자를 택한다.** 근거는 §2 Q1·Q8. 그리고 이 선택의 대가를 **화면 문구로 정직하게 말한다** —
"앱을 닫아도 알려드립니다"라고 쓰지 않는다. 이 앱에서 가장 위험한 실패는 조용히 성공한 척하는
것이고(§4 계약, `sync-chip`), **오지 않는 알림을 기다리게 하는 것**이 정확히 그 실패다.

### Q1. 좌표를 서버에 저장할 것인가 — **아니다**

G3가 `lib/discovery/nearby.ts` 헤더에 적어 둔 세 규칙을 N1은 **완화하지 않고 강화한다.**

1. `navigator.geolocation`은 **명시적 탭에서만** 호출한다. 마운트 시 묻는 effect는 없다.
2. fix는 React state에 있고 거기서 끝난다. localStorage·아웃박스·요청 바디 어디에도 없다.
3. 거부/미요청은 **정상 답**이다. `point`가 null이면 하위 거리도 전부 null이고, 화면은 지어낸
   도보 시간 대신 동네 이름을 인쇄한다.

N1이 추가하는 규칙:

4. **`getCurrentPosition`이 `watchPosition`으로 승격되지만, 소유자는 하나다.** 모듈 레벨 싱글턴
   watch 하나를 여러 화면이 구독한다. 화면마다 watch를 열면 배터리가 두 배로 든다.
5. **`document.visibilityState !== "visible"`이면 watch를 끊는다.** 백그라운드에서 어차피 안 오는
   콜백을 기다리며 watch를 열어 두는 것은 배터리만 쓴다. 복귀 시 재개.
6. **좌표에서 파생된 값도 저장하지 않는다.** 실측 fix로 계산한 도보 시간을 `stops.walk_minutes`에
   쓰지 않는다. 그 컬럼에 "그 순간 그가 그 매장에서 몇 분 거리에 있었다"가 들어가면 **역산으로
   위치가 저장된 것**이다. `walk_minutes`는 카탈로그 값이고 계속 카탈로그 값이다.

서버로 가는 것은 지금과 같이 **도시명 하나**다. `GET /api/recommendations?city=Toronto`.
N1은 **새 API 라우트를 하나도 만들지 않는다.** 판정 로직 전체가 브라우저에 있다.

> 저장하지 않는다는 것의 진짜 의미: **삭제할 것이 없고, 유출될 것이 없고, 영장에 답할 것이 없다.**
> `memory_constraints`가 행 단위 동의로 얻은 성질을, 위치는 "행이 없음"으로 얻는다.

### Q2. 계정 삭제(마이그레이션 0007)와의 관계

**1·2단계는 새 테이블이 0개이므로 0007에 엮을 것이 없다.** 기기에 남는 것은 localStorage 키
하나뿐이고, 그것은 로그아웃과 계정 삭제 경로에서 **다른 `trail:` 키와 함께 지운다**(§4 F5).

3단계(웹 푸시)를 언젠가 연다면 그때 지켜야 하는 것을 지금 못박아 둔다.

| 규칙 | 이유 |
| --- | --- |
| `push_subscriptions.user_id uuid not null references public.app_users(id) on delete cascade` | 0007의 캐스케이드는 `auth.users → app_users → …`다. 단일 FK cascade면 자동으로 걸린다 |
| **복합 FK에 `on delete set null`을 쓰지 않는다** | 0007 결함 2가 정확히 그거다. 복합 FK에 `set null`을 걸면 `user_id`까지 NULL이 되고 NOT NULL 위반으로 **캐스케이드 전체가 죽는다** |
| **append-only 트리거를 붙이지 않는다** | 0007 결함 1. 원장 트리거가 달린 테이블은 캐스케이드 DELETE에서 raise한다. 구독은 원장이 아니다 |
| **DB 삭제가 곧 구독 해지는 아니다** | 푸시 서비스(Apple/Google) 쪽 엔드포인트는 우리가 지워도 살아 있다. 계정 삭제 라우트가 **각 엔드포인트에 만료 요청을 먼저 보내고**, 실패해도 삭제는 계속한다 |
| 회귀 테스트 | "계정 삭제가 에러 없이 완료된다"는 0007이 이미 두 번 깨진 지점이다. 신규 테이블마다 이 케이스를 추가한다 |

### Q3. `Current Location → Shopping in` — **되돌리지 않는다**

`FIGMA_ADOPTION` §2 예외표 1행의 근거는 두 문장이었다.

> "이 값의 출처는 센서가 아니라 온보딩에서 여행자가 입력한 `trips.city`다. **앱에 위치 권한
> 경로가 없다.**"

N1은 **두 번째 문장만** 없앤다. **첫 번째 문장은 그대로다** — Home 카드가 그리는 값은 여전히
`trips.city`이고, 위치 권한이 생겨도 그 카드에 fix가 들어가지 않는다. 라벨을 `Current Location`으로
되돌리면 **타이핑된 값에 센서 출처를 주장하는** 것이 되어, 예외를 만든 이유가 오히려 강해진다.

두 값은 실제로 자주 다르다. 공항에서, 기차에서, 여행 전날 집에서 앱을 열면 `trips.city`는 Toronto고
fix는 Seoul이다. 하나의 라벨이 둘을 덮으면 **어느 쪽도 참이 아닌 화면**이 나온다.

**결정: 되돌리지 않고, 분리한다.**

| 자리 | 라벨 | 출처 |
| --- | --- | --- |
| Home 카드 | **`SHOPPING IN`** (현행 유지) | `trips.city` — 폼 입력 |
| 추천 레일 | `RECOMMENDATIONS NEAR YOU` (현행 §2에 이미 있음) | 카탈로그 + (있으면) fix로 정렬 |
| **신규 · 근접 배너** | **`NEAR YOU`** | **fix. 살아 있을 때만 존재** |
| **신규 · 상태 칩** | **`Using your location · Turn off`** | fix가 메모리에 있는 동안만 표시 |

**§2 예외표 요청 (`FIGMA_ADOPTION.md` 수정 1건)**: 1행을 삭제하지 말고 **이유 칸을 개정**한다.

> `이 값의 출처는 센서가 아니라 온보딩에서 여행자가 입력한 trips.city다. N1이 위치 권한을
> 열었지만 그 fix는 NEAR YOU 레일과 근접 알림에만 쓰이고 이 카드에는 들어오지 않는다.`

그리고 8행을 추가한다: `(신규) Near you / Using your location — 센서 출처를 쓰는 유일한 두 자리.`

> **부수 효과 하나가 중요하다.** `Using your location`은 장식이 아니라 **끄는 버튼**이다.
> 켜져 있다는 사실이 화면에 안 보이는 위치 기능은, 그 자체로 사용자가 동의를 철회할 방법이 없다.

### Q4. 알림 채널

| 채널 | 판정 | 이유 |
| --- | --- | --- |
| **인앱 배너** (앱이 화면에 보일 때) | **1단계로 채택** | 서버 0, 마이그레이션 0, 권한은 위치 하나뿐. §1에서 유일하게 100% 동작이 보장되는 채널 |
| **로컬 `registration.showNotification()`** (앱 실행 중, 알림 권한) | **2단계로 채택, 단 기대치를 낮춘다** | 앱이 **실행 중일 때만** 뜬다. 잠깐 다른 탭을 봤거나 방금 화면을 내린 직후 정도를 커버한다. iOS는 홈 화면 웹앱에서만 `Notification`이 존재하고, 백그라운드로 가면 JS가 멈춰 **사실상 배너와 같아진다** |
| **웹 푸시** (`PushManager` + VAPID) | **보류 — 지금은 만들지 않는다** | 아래 |

**웹 푸시를 지금 만들지 않는 이유는 기술이 아니라 데이터다.**

푸시는 우리 서버가 보낸다. "근처에 왔을 때" 보내려면 서버가 **언제 근처인지**를 알아야 하고,
그러려면 브라우저가 주기적으로 좌표를 올려야 한다. 그런데 §1에서 본 대로 **백그라운드에서는
브라우저가 좌표를 읽을 수조차 없다.** 즉 푸시를 붙여도:

- 앱이 켜져 있을 때만 좌표가 올라간다 → 그 순간엔 이미 인앱 배너로 알릴 수 있다
- **얻는 것: 거의 없음 / 내주는 것: 서버의 위치 이력 테이블 + 푸시 구독 테이블**

여기에 세 번째 대가가 붙는다. 푸시 본문은 **Apple/Google 푸시 서비스를 거친다.**
`"Kensington Market 근처에 …"`를 푸시로 보내는 순간 **제3자가 이 사람의 위치를 알게 된다.**
`VENTURE_BRIEF` §7.4가 이미 "호텔명이 매 턴 OpenAI로 가는 불필요한 3자 전송"을 결함으로 적었다.
같은 실수를 위치로 반복하지 않는다.

**재개 조건 (전부 충족돼야 다시 연다)**
1. `products`·`stores`에 `source='live'` 행이 실제로 존재한다 (§Q5 — 없으면 알릴 내용이 샘플뿐)
2. 좌표 보관 기한·해상도가 문서화된다 (§7.4 "배송 완료 후 이동 경로 삭제"와 같은 급의 정책)
3. `0030` 마이그레이션이 §Q2의 5개 규칙을 지킨 채 작성·적용되고 `get_advisors`를 통과한다
4. PIPEDA 관점 검토 — 위치는 민감 개인정보이고 동의 표준이 다르다
5. 푸시 본문에 매장명·수령인명을 넣지 않는 문구 규격 (§7)

### Q5. 알림 문구가 환각이 아니려면 — **`Sample`은 배지가 아니라 문장으로**

지금 `products`·`stores`의 시드는 전부 `source='sample'`이다(0023). 제품 규칙 3과
`FIGMA_ADOPTION` §1-1은 **행의 `source` 컬럼을 읽어** 표시하라고 정했다. 알림에는 배지를 붙일
자리가 없다 — **그러면 단어가 문장 안으로 들어간다.**

**규격 (§7에 전문)**
- **모델을 부르지 않는다.** 알림 문구는 템플릿이고, 값은 이미 화면에 그려진 행에서 온다.
  `/api/chat`은 알림 경로에 존재하지 않는다. **환각을 문구 검수가 아니라 구조로 막는다.**
- `source !== 'live'`이면 **제목에 `Sample`**이 들어간다: `Sample find near you`
- 본문 마지막 문장은 고정: `Sample data — stock isn't confirmed.`
- **재고·영업중·확정 가격을 말하지 않는다.** `store_hours`(0011)도 샘플이므로 "지금 열려 있어요"는
  쓰지 않는다. `price_is_estimate`가 true인 금액은 **알림에 아예 넣지 않는다** — 금액은 화면에서 본다
- **수령인 이름을 넣지 않는다.** 잠금화면은 공용 화면이다. `Someone on your list`로 쓴다
  (서프라이즈 보호이자 §Q8의 최소 노출)
- CTA는 `See it` — **`Buy`를 쓰지 않는다.** 제품 규칙 2, TRAIL은 주문하지 않는다

> **샘플이라서 알림을 안 보내는 선택지**도 검토했으나 기각한다. 카탈로그가 전부 샘플인 지금
> 그러면 기능이 영원히 안 뜨고, 그건 만든 적 없는 기능과 같다. **샘플이면 샘플이라고 말하고 보낸다.**
> 대신 §Q7의 하루 상한을 샘플일 때 **3건 → 2건**으로 낮춘다. 정직함은 빈도로도 표현된다.

### Q6. "내가 좋아하는 것" 등록 — **재사용. 마이그레이션 0건**

이미 있는 것으로 전부 된다.

| 필요한 것 | 이미 있는 자리 | 상태 |
| --- | --- | --- |
| 본인 취향 태그 | **`plans.preference_tags`** (0025, `public.preference_tag` enum 8종) | 있음. `/ask/brief`에 칩 UI까지 있음 |
| 본인이 수령인 | **`recipients.is_self`** (0001, unique 제약까지) | 있음. `(you)` 표시도 있음 |
| 매칭 대상 태그 | **`products.preference_tags`** (0023, GIN 인덱스) | 있음 |
| 경로 취향 | `plans.route_tag` + `withinRouteTag()` | 있음 |

**새 테이블을 만들지 않는다.** 이유는 비용이 아니라 정합성이다 — 별도 "내 취향" 테이블을 만들면
`/ask/brief`의 칩과 두 개의 취향이 생기고, 어느 쪽이 추천을 지배하는지 아무도 모르게 된다.

**매칭 규칙 — 추론 순서를 낮은 것부터**

| 순위 | 신호 | 추론 정도 | 쓸 것인가 |
| --- | --- | --- | --- |
| 1 | **아직 안 산 `planned` stop의 매장이 근처** | **0. 사용자가 직접 승인한 계획이다** | **쓴다** — 가장 정직하고 가장 유용하다 |
| 2 | 근처 매장의 상품 `preference_tags` ∩ `plans.preference_tags` | 낮음. 닫힌 enum 교집합 | 쓴다 |
| 3 | `recipients.preference_note` 자유 텍스트 파싱 | **높음** | **쓰지 않는다.** 브라우저가 "도자기 좋아함"을 태그로 바꾸는 것이 곧 환각이다 |
| 4 | `memory_constraints` | 해당 없음 | **쓰지 않는다.** 그 동의는 대화용이고 알림용이 아니다 |

1순위가 이 기능의 본체다. **"Mom 선물 사려던 그 가게에서 4분 거리입니다"**는 어떤 추천 알고리즘보다
정확하고, 데이터가 전부 사용자 자신의 승인된 계획에서 나온다. 그리고 이건 **N3(수령인 우선순위)와
바로 붙는다** — 우선순위 1번의 미구매 stop을 먼저 알린다.

> **작은 배선 부채 하나.** `lib/state/types.ts`의 `Stop`에는 `storeName`·`storeAddress`는 있어도
> **좌표가 없다.** DB의 `stops.store_id`는 존재하므로 **마이그레이션 없이** `STOP_SELECT`에
> `store:stores(lat,lng)` embed를 더하면 된다. 다만 `types.ts`·`queries.ts`·`shape.ts`는
> §4 계약상 "마이그레이션을 여는 그룹"이 만지는 파일이다. **N1-1a는 그 세 파일을 건드리지 않고
> 추천 피드의 store 좌표만 쓰고, 1순위 매칭은 N1-1b에서 G3와 조율해 배선한다.**

### Q7. 빈도 · 배터리 · 소음

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 위치 정확도 | `enableHighAccuracy: false` | GPS 대신 wifi/셀 측위. 250m 반경 판정에 GPS는 과하고 배터리를 먹는다 |
| `maximumAge` | 60_000 ms | 1분 된 fix로 충분하다 |
| 재판정 조건 | **직전 판정 지점에서 75m 이상 이동** 또는 **60초 경과** | 콜백마다 전 카탈로그를 도는 것을 막는다. 도보 75m ≈ 1분 |
| 진입 반경 | **250 m** | 도보 약 3–4분(`WALK_METRES_PER_MINUTE = 80`) |
| 이탈 반경 | **400 m** | 히스테리시스. 경계에서 서성일 때 알림이 깜빡이는 것을 막는다 |
| watch 중단 | `visibilityState !== "visible"` / 화면 이탈 / 20분간 이동 없음 / 로그아웃 | §1에서 어차피 안 오는 콜백을 기다리지 않는다 |
| 하루 상한 | **3건** (전 행이 `sample`이면 **2건**) | §Q5 |
| 최소 간격 | **20분** | 한 골목에 매장이 셋이면 셋을 한 알림으로 합친다 |
| 매장 재알림 | **여행당 1회** (하루 1회가 아니다) | 어제 지나친 가게를 오늘 또 알리면 그건 알림이 아니라 잔소리다 |
| 조용 시간 | `trips.timezone`(0021) 기준 **21:00–08:00 무음** | 폰의 시간대가 아니라 여행지 시간대. `greetingFor`가 이미 같은 규칙이다 |
| 기본값 | **꺼짐** | 켜는 것은 탭이다. 마운트 시 묻지 않는다 |

**기억은 어디 사는가 — 기기의 `localStorage` 하나**

```
키:  trail:nearby:v1:{userId}:{tripId}
값:  { alerted: { [storeId]: ISO8601 }, dayKey: "2026-08-18", dayCount: 2 }
```

- **좌표가 들어가지 않는다.** 매장 ID와 시각뿐이다. 이 파일을 통째로 훔쳐도 나오는 문장은
  "이 사람은 이 여행에서 이 가게들의 알림을 받았다"이지 "어디에 있었다"가 아니다.
- 접두사 `trail:nearby:v1:`은 `trail-cache-v4/v5:*`(오프라인 아웃박스·구매 초안)와 겹치지 않는다.
  §4 계약대로 **어떤 스윕도 하지 않는다.**
- 상한 200 엔트리 LRU. `dayKey`가 바뀌면 `dayCount`만 리셋하고 `alerted`는 유지(여행당 1회 규칙).
- 로그아웃·계정 삭제·여행 아카이브 시 삭제.
- **서버로 동기화하지 않는다.** 기기를 바꾸면 알림이 한 번 더 올 수 있다. 그 대가를 받는다.

### Q8. 스토킹 도구가 되지 않으려면

G6는 "무엇을 내보내지 않는가"를 화이트리스트로 정했다. N1은 내보낼 화면이 없으므로 대칭형으로
**"무엇을 적지 않는가"**를 정한다. 전문은 §6. 핵심 셋만 여기서:

1. **fix에서 나온 어떤 값도 영속화하지 않는다.** 좌표도, 거리도, 도보 시간도, "근처였다"는 사실도.
   유일한 예외가 §Q7의 `{storeId: 시각}` 맵이고, 그것도 기기 안이다.
2. **알림 내용이 곧 위치 정보다.** 그래서 수령인 이름을 넣지 않고, 푸시(제3자 경유)를 만들지 않는다.
3. **G6 공유 투영에 위치가 새지 않도록 회귀 테스트를 확장한다.**
   `tests/share-projection.test.ts`의 거부 문자열 스캔에 `lat|lng|coord|geo|distance|nearby`를 더한다.
   2단계 공동 편집(`0027~0029`)이 오면 "소유자가 지금 어디 있는지"는 **멤버에게도 안 보인다** —
   N1의 상태가 애초에 행이 아니므로 이건 자동으로 성립하고, 그 성립을 문서로 못박는다.

> 그리고 이 기능의 존재 자체가 사회공학 표면이다. **"Trail이 근처 알림을 보냈어요"라고
> 주장하는 이메일**은 좋은 피싱이 된다. 알림은 앱 안에서만 만들고, 이메일 채널을 열지 않는다.

| — | **N1-0 / N1-1 / N1-2** | N1 | **번호를 배정하지 않는다.** 필요한 컬럼이 전부 이미 있다 |
| `0030` | `push_subscriptions` (N1-3) | N1 | **요청 보류.** §Q4 재개 조건 5개 충족 전에는 원장에 올리지 않는다 |

**원장에 남길 요청 한 줄**: `N1(위치 기반 알림)은 1~2단계에서 번호를 쓰지 않는다. 3단계(웹 푸시)를
열 때만 0030을 요청한다.` — 번호를 미리 잡아 두면 "이미 자리가 있으니 만들자"가 되기 때문에
**잡아 두지 않는 것 자체가 결정이다.**

없는 것을 만들지 않기 위해 확인한 것: `stops.store_id`(0001) · `stores.lat/lng`(0001) ·
`store_hours`(0011) · `trips.timezone`(0021) · `products.preference_tags` + `preference_tag` enum(0023) ·
`plans.preference_tags`(0025) · `recipients.is_self`(0001) — **전부 있다.**

## 6. 저장하지 않기로 한 것 — 명시적 목록

G6 §3의 화이트리스트에 대응한다. 여기 있는 것은 **어떤 토글로도 켜지지 않는다.**

| # | 저장하지 않는 것 | 어디에도 없다는 뜻 |
| --- | --- | --- |
| 1 | **위도·경도** | DB · localStorage · sessionStorage · 아웃박스 · 요청 바디 · URL · 쿠키 · 로그 · 애널리틱스 |
| 2 | `accuracy` · `altitude` · `heading` · `speed` | fix 객체에서 `lat`/`lng`만 읽고 나머지는 애초에 안 꺼낸다 |
| 3 | **위치 이력 / 타임스탬프가 붙은 어떤 지점** | "여기 몇 시에 있었다"는 행이 존재하지 않는다 |
| 4 | **체류 시간(dwell)** | 진입/이탈 판정은 메모리에서 일어나고 그 결과만 남는다 |
| 5 | **실측 fix로 계산한 도보 시간·거리** | `stops.walk_minutes`에 쓰지 않는다. 그 컬럼은 카탈로그 값이다 |
| 6 | **구매의 위치 태깅** | `purchases`에 "어디서 기록했는지"를 붙이지 않는다 |
| 7 | 이송 이벤트의 위치 | `transfer_events`는 지금도 좌표를 안 받는다. **N1이 그 문을 열지 않는다** |
| 8 | **좌표가 섞인 AI 프롬프트** | `app/trail-brief.ts`에 위치 필드를 추가하지 않는다. §7.4 P0-3의 반복 금지 |
| 9 | **푸시 구독 엔드포인트** | N1-3 전에는 테이블도 코드도 없다 |
| 10 | **매장 방문 기록** | 알린 것과 간 것은 다르다. 후자는 아예 관측하지 않는다 |
| 11 | 알림 기억의 **좌표 필드** | `alert-memory.ts`의 인자에 좌표 타입이 없다 (컴파일러가 막는다) |
| 12 | **알림 기억의 서버 동기화** | 기기당이다. 기기를 바꾸면 한 번 더 온다 |
| 13 | **수령인 이름이 담긴 알림 문구** | 잠금화면·푸시 서비스·스크린샷 어디에도 |
| 14 | **공유 링크의 위치** | G6 투영 화이트리스트에 위치 항목을 추가하지 않는다. 거부 스캔이 지킨다 |
| 15 | **멤버에게 보이는 소유자 위치** | G6 2단계에도 열지 않는다. 행이 없으므로 열 것이 없다 |

## 7. 알림 문구 규격

**전부 템플릿이다. 이 경로에 모델이 없다.**

| 조건 | 제목 | 본문 | CTA |
| --- | --- | --- | --- |
| 계획된 stop, `source='sample'` | `Sample find near you` | `Something on your Toronto list is about 4 min from here. Sample data — stock isn't confirmed.` | `See it` |
| 계획된 stop, `source='live'` | `On your list, 4 min away` | `{store}, about 4 min from here.` | `See it` |
| 태그 매칭, `source='sample'` | `Sample find near you` | `Trail's sample list for Toronto has a handmade pick about 6 min from here. Sample data — stock isn't confirmed.` | `See it` |
| 매장 여러 곳 | `Sample finds near you` | `3 places on Trail's sample list are within a few minutes.` | `See them` |

**금지 표현**

| 쓰지 않는다 | 이유 |
| --- | --- |
| 수령인 이름 (`Mom's gift is nearby`) | 잠금화면은 공용 화면 · 서프라이즈 · §Q8 |
| `Open now` · `In stock` · `Available` | `store_hours`도 재고도 샘플이다. 제품 규칙 3 |
| 확정 금액 (`CAD $58`) | `price_is_estimate`가 기본 true. 금액은 화면에서 본다 |
| `Buy` · `Order` · `Reserve` | 제품 규칙 2. TRAIL은 주문하지 않는다 |
| 주소 · 미터 단위 거리 | `about {n} min`으로 반올림한다 |
| `You are at …` | 앱이 사용자에게 위치를 되읽어주지 않는다 |

**설정 화면이 반드시 말해야 하는 것 (N1-2)**

> `Nearby alerts only work while Trail is open on your screen. The web can't watch your
> location in the background — on iPhone, Trail stops running the moment you switch apps.`

이 문장을 안 쓰면 **오지 않는 알림을 기다리게 만든다.** 이 앱에서 가장 위험한 실패 유형이다.

## 10. 하지 말아야 할 것

1. **"백그라운드에서도 알려드립니다"라고 쓰지 마라.** §1에서 불가능하다고 판정했다. 이 문장 하나가
   기능 전체를 거짓말로 만든다.
2. **좌표를 서버로 보내는 라우트를 만들지 마라.** 편의를 위해서도, 로깅을 위해서도, "나중에 쓸지
   모르니"를 위해서도. **N1은 API 라우트가 0개다.**
3. **서비스워커에서 위치를 읽으려 하지 마라.** 노출되지 않는다. 폴리필도 없다.
4. **Geofencing API를 쓰려고 하지 마라.** 출시된 적이 없다. 문서를 봤다면 2016년 초안이다.
5. **Periodic Background Sync로 우회하려 하지 마라.** Chromium 전용이고, 깨어나도 위치가 없다.
6. **알림 문구를 모델에게 쓰게 하지 마라.** 템플릿이다. 이 경로에 `/api/chat`이 들어오는 순간
   환각이 잠금화면에 뜬다.
7. **`recipients.preference_note`를 파싱해 태그로 만들지 마라.** 자유 텍스트 → 닫힌 enum 변환이
   곧 추론이고, 그 추론에 근거 카탈로그가 없다.
8. **`memory_constraints`를 매칭에 쓰지 마라.** 그 동의는 대화에 준 것이다.
9. **실측 fix로 계산한 값을 DB 컬럼에 쓰지 마라.** 특히 `stops.walk_minutes`. 파생 위치도 위치다.
10. **알림에 수령인 이름·금액·재고·영업중을 넣지 마라.** §7.
11. **권한을 마운트에서 묻지 마라.** 위치도, 알림도. 거부당한 권한은 되돌리기가 훨씬 비싸다.
12. **G6 공유 투영에 위치를 추가하지 마라.** 토글로도.
13. **`0030`을 미리 잡아 두지 마라.** 빈 번호는 "만들어도 된다"는 신호가 된다.
14. **`shell.tsx`·`landing.ts`·`:root` 토큰을 만지지 마라.** §4 계약.
15. **G3의 "좌표는 기기를 떠나지 않는다" 주석을 지우지 마라.** N1은 그 문장을 지키러 온 것이지
    풀러 온 것이 아니다.
