# TRAIL 팀 내부 설문 — "실제로 작동하는 버전"까지 (v1)

> **웹 버전: `/survey/team`** — 배포·자극물·응답 내려받기는 [WEB.md](WEB.md). 문항을 고칠 때는 이 파일과 `lib/survey/`를 같이 고친다.

대상: TRAIL을 실제로 만들고 있는 팀원 전원 (TF 7개 역할 + 실제 작업자)
목적: 와이어프레임을 **돌아가는 제품**으로 바꾸는 데 필요한 세 가지를 확인한다.
  ① 지금 뭐가 진짜로 되고 뭐가 화면뿐인지에 대한 **인식이 서로 같은가**
  ② 남은 것 중 **뭘 먼저** 붙일지 합의가 되는가
  ③ 각자 **어디서 막혀 있는가** (그리고 그걸 아직 아무도 말 안 했는가)
방식: 익명. 역할만 받고 이름은 받지 않는다. 소요 **12–15분**.
주기: 지금 1회 → 데모데이 2주 전 1회 (같은 문항으로 재측정해 변화를 본다)

> **이 설문의 핵심 지표는 평균이 아니라 분산이다.**
> §2에서 같은 항목을 두고 답이 갈리면, 그건 의견 차이가 아니라 **팀이 서로 다른 제품을 만들고 있다는 신호**다.
> 그래서 §2를 맨 앞에 두고, 응답 전 문서(HANDOFF·MIGRATION_PLAN)를 **열어보지 말고** 답하게 한다.

## §2. 현황 인식 — 지금 뭐가 진짜로 되나 🔑

**문서를 열지 말고**, 기억나는 대로 각 항목을 판정해 주세요. 모르면 **"모른다"** 를 고르는 게 정답입니다.

판정 척도: `동작한다(써 볼 수 있다) / 코드는 있으나 안 붙었다 / 디자인·문서만 있다 / 아예 없다 / 모른다`

| # | 항목 |
| --- | --- |
| P-01 | 여행 등록 → 수령인 등록 → 예산 배분이 서버에 저장된다 |
| P-02 | Trail AI 대화가 구조화된 brief로 바뀐다 |
| P-03 | AI가 말하는 **매장 이름**이 실재하는 매장이다 |
| P-04 | 예산 초과 시 승인 게이트가 **DB 권한으로** 강제된다 |
| P-05 | 매장에서 구매를 기록하면 실제 지출이 반영된다 |
| P-06 | 지도 탭이 실제 지도·경로로 동작한다 |
| P-07 | 배송 결제가 **실제 돈**을 움직인다 |
| P-08 | 배송 상태가 시스템에 의해 자동으로 올라간다 |
| P-09 | 파트너 매장에서 QR/태그를 붙이는 절차가 코드로 존재한다 |
| P-10 | 오프라인(비행기 모드)에서 QR 패스를 쓸 수 있다 |
| P-11 | 로그인이 실제로 동작한다 |
| P-12 | 앱이 **공개 URL로 배포**되어 있다 |
| P-13 | 계약된 파트너 매장이 한 곳 이상 있다 |
| P-14 | 계약된 호텔이 한 곳 이상 있다 |
| P-15 | 실제로 완료된 배송이 한 건 이상 있다 |

**P-16.** 위 15개 중 **본인이 직접 확인해 본 것**은 몇 개입니까? `0 / 1–3 / 4–7 / 8–11 / 12+`

> **분석 (이 설문에서 가장 중요한 부분)**
> - 항목별 **최빈답 일치율**을 낸다. 일치율 70% 미만 항목 = 인식 분열 지점 → 그 항목은 다음 회의 안건으로 강제 상정.
> - **"모른다" 비율이 40%를 넘는 항목**은 그 자체로 문제다. 팀 절반이 모르는 기능은 데모에서 자신 있게 시연할 수 없다.
> - **낙관 편향**: 실제 상태(`docs/VENTURE_BRIEF.md §0`, `docs/HANDOFF.md`)보다 후하게 답한 항목 수를 응답자별로 세어 분포를 본다. 팀 전체가 후하면 데모 당일 사고가 난다.
